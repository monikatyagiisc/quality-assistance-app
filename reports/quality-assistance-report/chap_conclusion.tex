\chapter{Conclusions}
\label{chap:conclusion}

This project aims to address the gaps between different software quality activities by developing an AI-assisted application that supports various stages of the Software Testing Life Cycle (STLC). The prototype brings together a React and TypeScript frontend, a FastAPI backend, a PostgreSQL database, and a separate agent service built using Google's Agent Development Kit (ADK). At the centre of the system is a root agent that understands incoming requests and directs them to nine specialised agents. Each agent focuses on a particular testing activity, including test-case design, test-data generation, automation suggestions, execution analysis, self-healing recommendations, change-impact analysis, defect reporting, test summaries, and release-readiness assessment.

Along with these capabilities, the application provides user authentication and stores submitted requests for future reference. It also integrates with Jira Cloud to access issue details and GitHub to retrieve code changes. Additional features include optional Microsoft Entra single sign-on and support for configuring different AI model providers.

The prototype shows how multiple testing-related activities can be brought together within a single application and supported through specialised AI agents. However, further evaluation is needed before drawing conclusions about its actual benefits. At this stage, there is no experimental evidence to establish whether the system improves test coverage, reduces the overall effort required by quality engineers, or helps identify more defects. The agents are intended to assist engineers by providing suggestions and organising relevant information, not by replacing their judgement.

It is also important to understand the limitations of the current implementation. The execution analysis agent reviews available test results but does not run test suites on its own. Similarly, the self-healing agent suggests possible changes to automation scripts but does not apply those changes automatically. The release-readiness assessment provides supporting information for decision-making; the final decision to approve or reject a release remains with the responsible team.

\section{Future Work}
The next steps I have identified, in order:
\begin{enumerate}
  \item Structured outputs and checks between specialist stages;
  \item An explicit approval step and editing of individual cases, building on the refine-and-rerun loop that already exists;
  \item An evaluation of traceability, correctness, review effort, latency, and cost against a baseline written down in advance;
  \item Trials on public projects and, after approval, on anonymized organisational artifacts;
  \item Retrieval over approved requirements, test repositories, and historical defects;
  \item A careful CI/CD hook for test execution, and session history that survives a restart and can be audited; and
  \item Load, reliability, accessibility, privacy, and security reviews before this is treated as a wider deployment.
\end{enumerate}

I already know an LLM can write something that looks like a test case. The question I still cannot answer is whether this orchestrated assistant produces work that people can trace and use, often enough that the review it creates is still cheaper than doing the task without it. The prototype is the place to run that comparison. Screenshots of a working demo are not the comparison.
